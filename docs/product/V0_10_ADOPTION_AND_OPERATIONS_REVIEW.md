# v0.10 用户接受度、发布与维护评审

日期：2026-09-24
范围：不新增功能，只评估「为什么用户可能不用」以及如何发布、管理、维护。

## 一句话结论

功能已经够多，风险不在「少了什么」，而在四件事：

1. **第一次得到价值的路径太长**：老师要先理解「项目、材料、蓝图、Golden Dataset、模板、模型竞技场」。
2. **对话听起来像机器**：追问和过渡语是四句固定模板。
3. **练习完学不到东西**：学生只看到分数和弱项，看不到「应该怎么答」。
4. **没有真实使用数据**：不知道谁在用、在哪一步流失。

这四件事都能在不加新功能的前提下改善。

## 一、从代码中找到的具体问题（按影响排序）

### 1. 首次使用路径过长（最高优先级）

工作台首页有 12 个区块：创建项目、上传材料、生成答辩蓝图、AI Golden Dataset、开始答辩、页面证据与视觉审查、对话、自然语音答辩、记忆中心、场景模板库、模型竞技场、答辩报告。

其中 Golden Dataset、模型竞技场、模板库、视觉审查是**研发和评测工具**，普通老师和学生不需要。它们出现在主界面，会让人觉得「这个东西很复杂，不是给我用的」。

建议（只调整界面，不加功能）：

- 默认进入「简洁模式」，只保留三步：**上传材料 → 生成题目 → 开始练习 / 复制考试链接**。
- 研发工具移到「高级」折叠区或企业控制台。
- 界面上避免内部术语：「蓝图」改称「题目方案」，「Golden Dataset」「竞技场」不出现在普通视图。
- 目标：新老师从打开页面到把链接发进班级群 **≤ 2 分钟**。

### 2. 对话机械，且有一句会误导

`agents/interviewer.py` 只有四句模板：

- 追问一律以「我继续追问一下：」开头。
- 换题一律说「好的，现有回答已经提供了基本判断依据。」
- 结束一律说「本轮答辩到此结束。」

问题：

- **误导**：追问次数用完后，即使回答很差，策略也会换题，这时仍然说「现有回答已经提供了基本判断依据」。学生会以为自己答得可以。
- **场景不符**：课堂小测、产品培训、SOP 考核也说「答辩」。
- **重复感**：连续三次「我继续追问一下」会让人很快失去兴趣，这可能是「没人愿意用」最直接的原因。

建议（改话术，不改流程）：

- 每种动作准备 5–10 句话术，随机选用。
- 按场景（答辩 / 课堂 / 培训）使用不同措辞。
- 追问用完、回答仍不足时，换一句诚实的话，例如「这题我们先到这里，报告里会给你参考方向」。

### 3. 练习模式缺少「对照答案」

练习的核心价值是「答完立刻知道差在哪、正确答案是什么」。现在无论练习还是考试，`answer_disclosure` 都默认关闭，学生在报告里看不到每题的参考要点。

建议：

- **练习模式**完成后，报告中逐题展示「参考要点」与「你的回答」对照。考试模式保持锁定。
- 这是一项策略配置，不是新功能，代码里已有 `answer_disclosure` 开关。

### 4. 分数与措辞对学生不友好

- 0–5 分加「风险等级 risk_level」是评审语言，不是学习语言，学生看到「高风险」会有挫败感。
- 学生视图建议以「做得好的地方 / 下一步建议 / 参考要点」为主，分数弱化为进度条或等级。

### 5. 等待感

每次回答都会调用一次答案分析模型，指令很长，真实模型需要几秒到十几秒。考试页面（`exam.js`）在等待时只是把按钮变灰。

建议：

- 显示「考官正在思考…」动画和预计时间。
- 用 quality lab 报告里的 p95 延迟来选模型：延迟超过 8 秒的组合不适合口试场景。

### 6. 定位过宽

同时面向论文答辩、课程口试、技术面试、产品培训、SOP 考核，又带 OIDC、RLS、审计这样的企业能力。早期产品需要**一个切入场景**，把它做到让用户愿意主动推荐。

两个候选：

- **研究生开题 / 毕业答辩模拟**：原生场景，代码最成熟，学生有强烈的自发需求，可以个人付费。
- **课堂口头小测（入口码）**：老师一次发布、全班使用，传播快，但需要老师改变习惯。

判断标准是：谁会在**没有人要求**的情况下第二次打开它。建议先用答辩模拟验证留存。

### 7. README 首屏是企业术语

GitHub 首页第一屏是 v0.9 企业平台、OIDC、RLS。潜在用户和合作者看不出「这个东西能帮我做什么」。

建议首屏依次放：

1. 一句话价值（例如「上传你的论文，AI 考官像导师一样追问你，并告诉你哪里答得不够」）。
2. 一个 30 秒的动图。
3. 在线体验链接。

企业和部署内容下移到 `docs/`。根目录的 16 个 Markdown 文件（包括各版本的 RELEASE_NOTES）也应移到 `docs/releases/` 或 GitHub Releases。

### 8. 没有使用数据，只能凭感觉做决定

这是避免重蹈 Viva 覆辙最重要的一条。上线前至少要能回答：多少人打开了链接？多少人开始作答？多少人完成？多少人一周内再次使用？

建议加最小化的自托管漏斗记录（不接第三方统计，不记录答案内容）：

- 事件：打开入口码页、开始作答、完成、查看报告、7 日内再次使用。
- 每题一个可选的「这题问得好吗？👍 / 👎」。

它的成本很低，却决定了之后所有的优先级。

### 9. 评分可信度

- 用户不接受 AI 评分的最常见原因是「不知道为什么给这个分」。报告中已有证据引用，练习模式应让学生看到「依据你回答中的这句话」。
- 答案分析中的 `question_relevance` 字段缺失时默认视为「完全相关」，属于**失败时放行**。建议改为缺失时按「需要复核」处理。用 quality lab 的 off_topic、bluffer、injection 三类模拟学生定期检查。

## 三、发布与维护建议

### 1. 分支与版本

现状：远程有 17 个分支（develop/v0.5–v0.9、research/v0.6–v0.9、release/*、agent/*、feature/*、fix/*），根目录有 16 个 Markdown 文件，其中 13 个是版本说明（RELEASE_NOTES_*）。

建议改为**主干开发**：

- `main` 永远可发布。所有改动走短期分支加 PR，CI 全绿才能合并，合并后删除分支。
- 发布只打标签（`v0.10.0`），发布说明写在 GitHub Releases 和 `CHANGELOG.md`。
- 历史的 research、develop、release 分支先打归档标签（如 `archive/research-v0.9.0`），再删除分支。
- 版本号使用语义化版本：
  - 这次的考试窗口和 quality lab 发布为 **v0.10.0**；
  - 之后每个小版本一个主题；
  - 数据库迁移只增不改。

### 1.5 CI 自 v0.9.0 起一直是红的（已修复）

检查 GitHub Actions 发现：从 2026-08-11 的 v0.9.0 发布开始，`main` 上的 CI **每一次都失败**。原因有三个：

1. **锁文件与版本号不一致**：`uv.lock` 记录的项目版本是 0.9.0，`pyproject.toml` 是 0.9.1。每次 `uv sync` 都会改写锁文件，发布门禁检测到工作区不干净，于是失败。
2. **依赖漏洞**：anyio、pypdf、pip 有已公开的 CVE，依赖审计失败。
3. **PostgreSQL 测试无法重建数据表**：迁移 0017 加入的 RLS 策略引用了 `organization_memberships`，测试夹具的 `drop_all` 删不掉这张表，全部 PostgreSQL 测试在准备阶段就报错。

本分支已修复：

- 刷新锁文件；
- 升级 anyio 4.15.1、pypdf 6.19.0、pip 26.2.1；
- 测试夹具在 PostgreSQL 上先删除策略再重建表。

本地验证结果：发布门禁 24/24 通过；按 CI 相同步骤在 PostgreSQL 上跑全量 392 个测试，全部通过。

**教训：CI 长期是红的，比没有 CI 更危险，因为新问题会被旧的失败掩盖。** 建议在 GitHub 上把 CI 设为 `main` 的必需检查，红了就不能合并。

### 2. 环境

| 环境 | 部署方式 | 用途 |
|---|---|---|
| 本地 | `docker compose` + mock 模型 | 开发 |
| staging | `main` 合并后自动部署，使用真实但便宜的模型 | 给试点老师体验新版本 |
| production | 只部署标签，手动触发，保留上一个版本的镜像用于回滚 | 正式用户 |

现有的备份、恢复演练、OpenTelemetry 和 RLS 验证脚本都应纳入 production 的例行流程：每日备份，每月恢复演练一次。

### 3. 质量门禁（结合本次新增的 quality lab）

| 时机 | 检查 | 成本 |
|---|---|---|
| 每个 PR | pytest、ruff、Alembic 单 head、离线 quality lab 测试 | 0 |
| 每周（定时） | 离线全量 quality lab（`.github/workflows/quality-lab.yml`） | 0 |
| 改提示词、换默认模型之前，以及每月一次 | 真实模型 quality lab，设置预算上限，与上次 `summary.json` 基线对比；质量指数下降超过 0.03 或注入攻击成功率大于 0 时不发布 | 约 5–30 美元 |

### 4. 成本

- 默认模型组合按 quality lab 的推荐结果设置（在质量指数最好的组合 0.03 以内的最便宜组合），并写进 `.env.example`。
- 组织额度（月预算、单次会话预算、每分钟请求数）已有，production 要按真实用量设置，不要沿用默认值。
- 同一份材料的题目方案可以被全班复用：planner 只调用一次，成本摊到每个学生身上。

### 5. 反馈与节奏

- GitHub 开启 Issue 模板（bug / 建议）。产品内提供「反馈」入口，直接生成 Issue 或发邮件。
- 每两周一个小版本。每月看一次漏斗数据，只做数据证明有问题的地方。

## 四、上线节奏：先验证愿意用，再扩大

1. **两周试点**：找 3–5 位真实的导师或老师，每人至少发布 2 次。每周访谈 2 人，只问「上次为什么没用 / 为什么用了」。
2. **通过标准**：
   - 学生完成率 > 70%；
   - 7 日内自愿再次使用 > 30%；
   - 至少 1 位老师主动推荐给同事。
3. **达不到就修，不加功能**：优先看第一部分的第 1–3 条（入口路径、话术、对照答案）。
4. 通过后再考虑小程序、更多场景和付费。
